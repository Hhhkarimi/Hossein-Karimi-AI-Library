# Project definition and handoff

Use at MAP to turn prioritized opportunities into distinct projects. Give every candidate an ID, title, process, owner, intended outcome, priority rationale and disposition (define, discover, defer or reject). Write a separate charter for each project recommended for approval or pilot. Group shared enablers as separate work packages with explicit dependencies and allocated costs. Tie every charter to the portfolio ID and AIMPACT gates.

## Project charter

1. **Mandate and scope.** Describe the current workflow, affected users/sites, measurable problem, proposed change, boundaries and excluded decisions. Name the sponsor, accountable process owner and technical lead. Mark unassigned roles explicitly.
2. **Outcome and baseline.** Define KPI formula, unit, cohort, baseline period and source. Separate process outcomes, model quality, adoption and guardrails. Record target, evidence status and approving owner. When baseline or target is missing, assign a measurement task and an approval gate.
3. **Solution and work packages.** Describe the workflow before and after, the human decision point, data and integration contracts, sourcing choice and fallback. For each work package list deliverable, accountable role, dependency and acceptance evidence. Include discovery, pilot, production readiness and scale only where applicable.
4. **Investment and capacity.** Link the decision card and cost model. Separate pilot funding, production commitment and recurring staffing. State capacity assumptions and unresolved vendor or security prerequisites. Assign owners for shared dependencies and distinguish allocated from incremental cost.
5. **Pilot protocol.** Define comparison method and representative cohort, data split where relevant, minimum evidence or observation volume and how it is chosen, metric thresholds and unacceptable errors. Give pass, revise and stop criteria with the decision-maker. Specify shadow/manual mode and rollback triggers for operational workflows.
6. **Production handoff.** Name the service owner, support route, access controls, incident response, monitoring thresholds, fallback, training and change approval. Define what must be true before another site can adopt the solution.
7. **Decision requested.** State the current gate, approval requested, spending ceiling if available, blockers, next deliverable and accountable owner. Distinguish proposed from approved values.

## Quality check

Cross-check charter IDs, owners, KPI definitions, cost assumptions and dependencies against the portfolio and roadmap. Keep the ranking separate from funding approval. If a project cannot pass a hard gate, define the discovery work needed to resolve it or explain why it is deferred. In provisional outputs, make assumptions explicit and provide a usable next action for each unknown that could change the decision.
